# 2026-10-14 开盘首批数据延迟

## 已确认的故障

9:38 前确实没有完成今天首批页面发布。第一批在 9:38:30 才发布，扫描与发布总耗时 510.296 秒，其中扫描 382.838 秒、发布 127.458 秒。该批最新有效报价为 9:31:12，不能把发布时间当成行情时间。

当时同一工作区有两个服务：PID 14928 监听 8848，PID 7656 监听 8849。两个服务争抢同一个 pipeline.lock。7656 成功发布今天的数据，但用户访问的 8848 服务仍保留昨天的进程内状态，反复报告 PipelineBusy；磁盘页面、UI 数据版本与状态接口不一致。

重复服务产生的机制：原启动仅靠 1.5 秒 HTTP 探活判断单实例，探活失败后会尝试其他端口。慢初始化或发布期间的超时会把仍活着的服务误判为不存在，第二个服务可以在 8849 启动。守护程序的探活超时也可能触发此路径。

## 本轮修复

- 停掉 8849 的重复服务，让正在计算的 8848 服务先完成本轮发布，避免中断正在写入的数据。
- 为整个服务生命周期增加独立的操作系统文件锁 serve.instance.lock。即使探活超时，同一工作区的第二个服务也不能进入启动、扫描或端口绑定阶段。锁由操作系统管理，进程退出后可重新获取；没有删除更新锁或放松行情校验。
- 重新启动唯一服务与守护程序，使用已经验证可运行的 Codex Python。运行服务为 PID 16100，只监听 8848；服务单实例版本为 workspace-single-service-2026-10-14.1。
- 没有修改页面布局、风格、筛选因子或强度参数。
